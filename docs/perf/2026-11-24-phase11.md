# 성능·메모리 검증 — v2.4.1 vs v2.5.0-alpha.11 (2026-11-24, Phase 11-3)

- 도구: 세션 작업 공간의 Playwright 측정 스크립트(저장소 미포함, 2026-11-23과 같은 계열), Linux Chrome, 1600×1000, 오프라인.
- 대상: 재구축 `warehouse_layout_designer_v2_5_0-alpha_11.html`(sha256 22a1c674…), 기준본 `warehouse_layout_designer_v2_4_1.html`. 가상 배치 샘플·56·200·500·1000랙.
- 전체 측정을 2회 반복했고, 표는 항목별로 두 회 중 더 좋은(작은) 값을 양쪽 앱에 같은 방식으로 적용했다. 단위 ms(heap은 MB, 저장소는 KB).
- 실행하지 않음(NOT RUN): Windows Edge, 실제 마우스·터치패드 관성, 모바일.

## 실행취소 이력 메모리 (500랙, 선택한 랙을 방향키로 이동, GC 후 heap MB)

이력 상한은 `src/core/history.js`의 `limit = 60`(기준본과 같음). 이력은 전체 복제가 아니라 변경 연산(diff)만 저장한다.

| 편집 횟수 | 0 | 50 | 100 | 200 | 300 | 400 | 600 | 200회 편집 후 200회 되돌린 뒤 |
|---|---|---|---|---|---|---|---|---|
| 재구축 | 7.3 | 10.0 | 12.8 | 20.5 | 17.4 | 17.4 | 18.0 | 20.4 |
| v2.4.1 | 11.9 | 90.0 | 107.5 | 112.2 | - | - | - | 112.1 |

- 재구축: 0→200회에서 약 13MB 늘고 300회 이후 17~18MB에서 멈춘다(상한 60 도달 후 평탄). 600회 별도 실행으로 확인(0·50·100·200은 첫 실행과 일치).
- v2.4.1: 첫 50회에서 약 78MB 증가 후 112MB 부근. 단계마다 프로젝트 전체 복제를 보관하는 구조로 보이며 같은 키(방향키 이동)로 비교했다.
- 되돌려도 heap이 줄지 않는 것은 되돌린 단계를 다시 실행 목록에 보관하기 때문이다.

## 페이지 오류
- 모든 측정(2회 × 2앱 × 5규모, 실행취소 측정 포함)에서 페이지 오류 0건.

## 해석
- 게이트(500랙 이하 모든 항목에서 재구축이 기준본보다 오차 범위를 넘어 느리지 않음): 대부분의 항목이 재구축이 빠르다. 500랙에서 선택 524→44ms, 끌기 183→46ms, 확대·축소 324→34ms, 저장 완료 506→339ms. 1000랙에서도 모든 항목이 빠르다.
- 예외 1건: 56랙 '편집 1회 저장 완료'가 재구축 96~100ms, 기준본 82~83ms로 두 회 모두 약 15ms 느리다(샘플 규모에서도 80~118ms로 변동). 저장 쓰기 후 읽기 검증 단계의 고정 비용으로 추정되며 원인은 미확인. 200랙 이상에서는 재구축이 빠르다.
- 메모리·저장소: 모든 규모에서 heap과 저장소 사용량이 기준본보다 작다(1000랙 저장소 666→180KB).
- 단일 PC 측정이라 ±20% 안팎은 오차일 수 있다.
